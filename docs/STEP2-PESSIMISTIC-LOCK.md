# 2-2단계 ④ 비관적 락 — 오버부킹 방어와 구현 당시 예비 비교

> 이 문서는 `@Lock(PESSIMISTIC_WRITE)`(→ `SELECT ... FOR UPDATE`)가 오버부킹을 결정적으로 없앤다는
> 것과, 구현 당시 ②(조건부 UPDATE)와 수행한 예비 비교를 함께 기록한다. 락(④⑤)은 ②가
> 부족해지는 지점을 보여주기 위한 **대조군**이지 기본 해법이 아니다
> ([실험 통제 원칙](STEP2-3-BRANCH-STRATEGY.md#lock-experiment-control)). ②의 근거는
> [STEP2-CONDITIONAL-UPDATE.md](STEP2-CONDITIONAL-UPDATE.md), baseline 재현은
> [STEP1-BASELINE-OVERBOOKING.md](STEP1-BASELINE-OVERBOOKING.md)를 정본으로 한다.
>
> **측정 범위 주의.** 이 문서 4-2의 7쌍 수치는 ④ 구현 당시의 예비 측정이다. 현재 정본인
> [2026-09-25 방법론 v2 재측정](STEP2-DEFENSE-BENCHMARK.md#conditional-vs-pessimistic)은 Phase당
> 10라운드의 Williams 균형 순서를 사용한다. 2026-09-24 고정 순서 60회도 변경 불가한
> `methodology-v1-fixed-order` [원시 자료](benchmark/raw-runs.csv)와
> [실행 기록](benchmark/2026-09-24-controlled-run.md)으로만 보존한다. 역사 수치와 당시 해석은
> 구현 과정을 설명할 뿐 현재 선택 근거로 사용하지 않는다.

## 1. 고정 포맷 3문장 (현재 결론)

브랜치 전략이 ④⑤에 요구하는 세 문장을 먼저 적는다.

1. **왜 채택하지 않는가 — 최신 측정값까지 포함해서.** 비관적 락은 ②와 마찬가지로 오버부킹을
   0으로 만들었다. v2의 낮은 경합 평균 응답 중앙값은 Phase A/B 각각 ② 125.5/126ms,
   ④ 152/140ms였고, 극단 경합은 ② 117/122.5ms, ④ 88.5/97.5ms였다. 성능 방향이
   경합 지점에 따라 달라지므로 **보편적인 성능 열세는 미채택 근거가 아니다.** 현재 불변식은
   `UPDATE ... WHERE remaining > 0` 한 문장으로 완전히 표현되며, 그보다 넓은 명시적 잠금 구간이
   추가 정합성을 주지 않기 때문에 더 작은 상태 전이인 ②를 선택한다.
2. **이기는 조건은 무엇인가 — 전제로.** 비관적 락이 값을 하려면 임계 구역이 **여러 행·여러 문장에
   걸쳐** 한 문장으로 접을 수 없고, 경합이 높아 **재시도(낙관적) 비용이 대기 비용보다 커야** 한다.
   그때 락은 "읽은 것이 커밋까지 변하지 않음"을 보장해 다단계 로직을 안전하게 감싼다.
3. **그 조건이 이 도메인에 왜 없는가 — 뒤집히는 지점까지.** 이 도메인의 임계 구역은
   **카운터 하나를 1 줄이는 것**이 전부라 `WHERE remaining > 0` 한 문장으로 완전히 접힌다 —
   락이 지켜줄 다단계 구간 자체가 존재하지 않는다. 이 판단은 예약 확정이 **여러 자원을 원자적으로
   건드려야 할 때**(예: 좌석 감소 + 공용 쿼터 차감 + 결제 상태 기록) 뒤집힌다.

| 항목 | 값 |
|---|---|
| 방어 수단 | `@Lock(PESSIMISTIC_WRITE)` → `SELECT ... FOR UPDATE`, **스키마 변경 없음** |
| 막는 문제 | 오버부킹 (데이터 레이스) — **결정적으로 0** |
| **못 막는** 문제 | 같은 사용자의 중복 *요청/예약* — 락은 데이터 레이스만 다룬다. ①(V2 UNIQUE)의 몫 |
| ②와의 차이 | 결과는 동률(오버부킹 0). **접근이 반대** — ②는 레이스 구간을 없애고, ④는 남겨둔 채 잠근다 |
| 이 도메인에서의 평가 | **채택하지 않음** — 성능 열세 때문이 아니라 현재 불변식에 명시적 잠금 구간이 필요 없기 때문. 만석 거절 지연이 핵심 SLO라면 재검토 |

## 2. 무엇을 어떻게 구현했나

②가 read→check→write를 **DB 한 문장으로 접어** 레이스가 존재할 자리를 없앴다면, ④는 정반대다.
**baseline과 똑같은 read→check→write 구조를 그대로 두고**, 슬롯을 읽을 때 배타 락을 함께 걸어
그 구간을 직렬화한다.

```java
// 이 줄에서 SELECT ... FOR UPDATE 가 나간다. 이후 트랜잭션이 끝날 때까지 이 행은 내 것이다.
InterviewSlot slot = slotRepository.findByIdForUpdate(slotId)
        .orElseThrow(() -> new NotFoundException(...));

if (slot.isFull()) {          // ← 이 검사와
    throw new SlotFullException(...);
}
slot.decrease();              // ← 이 감소 사이에 아무도 끼어들 수 없다
```

락은 **트랜잭션 커밋/롤백까지 유지**된다(락 해제 코드가 따로 없는 이유다 — 트랜잭션 경계가 곧 락
경계다). 그 사이 같은 행을 읽으려는 다른 트랜잭션은 대기한다. baseline이 오버부킹을 냈던 바로 그
check-then-act가, 코드 모양은 그대로인 채 안전해진다 — **락이 무엇을 사는지**가 가장 선명하게
드러나는 지점이다.

| 경로 | 전략 | 오버부킹 | 방식 |
|---|---|---|---|
| `POST /api/reservations/baseline` | `ReservationService` | **발생**(간헐적) | 방어 없음 |
| `POST /api/reservations/unique` | `UniqueConstraintReservationStrategy` | **발생** | UNIQUE는 중복만 |
| `POST /api/reservations/conditional` | `ConditionalUpdateReservationStrategy` | **0** | 레이스 구간을 *없앤다* |
| `POST /api/reservations/pessimistic` | `PessimisticLockReservationStrategy` | **0** | 레이스 구간을 *잠근다* |

**부하 도구 확장.** `BaselineReservationSimulation`에 `-Dstrategy` 를 추가했다. 시나리오·구도는
그대로 두고 **때리는 경로만** 바꾼다(지정하지 않으면 1단계 baseline 경로 그대로라 step1 측정 자산은
훼손되지 않는다). 락마다 유리한 시나리오를 만들지 않는다는 실험 통제 원칙의 실행 수단이다.

**리포트에 이름표를 박는다.** Gatling 리포트 디렉터리는 `<시뮬레이션 클래스명>-<타임스탬프>` 뿐이고
`simulation.log` 에도 URL 경로가 남지 않는다 — 즉 `-Dstrategy` 만 추가하면 **쌓인 리포트 중 어느
것이 어느 전략의 측정인지 사후에 알아낼 방법이 없다.** 그래서 요청 이름에 실행 조건을 실었다.

```
reserve [pessimistic cap=1 cont=200]
```

이 이름은 `js/stats.js` 에 그대로 들어가므로 ⑦이 리포트를 기계적으로 파싱해 (전략 × 경합 수준)
2차원 표를 만들 때 자기 기술적인 키가 된다.

KO(진짜 실패) 0건. 데드락도 락 타임아웃도 관측되지 않았다.

> **📝 정정(2026-07-18, ⑤ 브랜치 작업 중 발견).** 이 자리에는 원래 *"잠그는 행이 하나뿐이라 락
> 획득 순서가 엇갈릴 수 없기 때문(데드락은 둘 이상의 자원을 서로 다른 순서로 잠글 때 생긴다)"*
> 이라고 적혀 있었다. **관측(데드락 0)은 그대로 참이지만 그 근거는 틀렸다.**
>
> 더 나쁜 것은, 이 근거가 **이 저장소가 1단계에 이미 기록해 둔 증거와 정면으로 모순**된다는
> 점이다. [STEP1-BASELINE-OVERBOOKING.md §5](STEP1-BASELINE-OVERBOOKING.md)는 baseline 이
> `reservation → interview_slot` **FK의 S→X 잠금 승격 데드락**으로 죽는 과정을 시퀀스 다이어그램
> 까지 그려 문서화했고, 그 절은 이렇게 끝난다 — *"정원 1짜리 **단일 행**에 경쟁이 몰리므로 이
> S/X 충돌이 대량 발생한다."* HTTP 부하에서는 요청의 **77%(387/500)** 가 이 데드락으로 죽었다
> ([STEP1-GATLING-LOADTEST.md](STEP1-GATLING-LOADTEST.md)).
>
> 즉 **1단계는 "단일 행이라서 데드락이 대량 발생한다"고, ④는 "단일 행이라 데드락이 불가능하다"고
> 적었다.** 같은 행, 정반대 결론이다. ⑤ 낙관적 락이 첫 구현에서 20건 중 19건 데드락을 내며
> 1단계와 똑같은 메커니즘을 그대로 재현했고, 그 과정에서 이 모순이 드러났다
> ([STEP2-OPTIMISTIC-LOCK.md 3절](STEP2-OPTIMISTIC-LOCK.md#3-이미-기록된-실패-모드의-재현--fk-데드락과-flush-순서)).
>
> **교훈:** 데드락은 "둘 이상의 자원을 다른 순서로 잠글 때"만 생기는 것이 아니라, **하나의 자원을
> 두고 락 등급을 올리려 할 때(lock upgrade)** 도 생긴다. 여럿이 공유 락을 나란히 쥔 채 전원이
> 배타 락을 요구하면 서로가 서로의 해제를 기다린다. **"단일 행이면 데드락이 없다"는 일반 명제로
> 성립하지 않는다** — 이 프로젝트는 그 반례를 두 번(1단계 baseline, ⑤ 첫 구현) 실측해 놓고도
> 이 문서에서 한 번 잘못 일반화했다.

**④가 데드락을 겪지 않은 진짜 이유는 행이 하나여서가 아니라, 배타 락을 먼저 잡아 승격을
없애기 때문이다.** 같은 FK, 같은 단일 행인데도 락 획득 순서가 셋 다 다르다.

```
1단계 baseline:  S(예약 INSERT 의 FK 검사) → X(커밋 시 remaining UPDATE)   ← 승격 → 데드락 77%
④ 비관적:       X(SELECT ... FOR UPDATE) → S(예약 INSERT 의 FK 검사)      ← 승격 없음 → 0건
⑤ 낙관적(첫 구현): S(예약 INSERT 의 FK 검사) → X(커밋 시 버전 UPDATE)      ← 승격 → 데드락 19/20
```

`SELECT ... FOR UPDATE` 는 임계 구역에 **들어가는 시점에** 배타 락을 잡는다. 그래서 한 번에 한
트랜잭션만 안으로 들어가고 나머지는 그 줄에서 대기하므로, 대기 중인 트랜잭션은 INSERT 에
도달조차 못 해 **공유 락을 쥘 기회 자체가 없다.** 승격할 S 락이 존재하지 않으니 교착이 아니라
대기열이 된다.

**여기서 락이 실제로 무엇을 샀는지가 드러난다.** ④는 baseline 이 겪던 데드락을 *우연히* 피한
것이 아니라, **잠금 순서를 강제**해 구조적으로 제거했다. 1단계에서 "데드락이 우연히 부분 방어처럼
작동한다"고 기록했던 그 부작용이 ④에서는 아예 발생하지 않는다. 락이 파는 것은 지연이고 사는
것은 **불확실성의 제거**인데, 그 불확실성에는 오버부킹뿐 아니라 **이 데드락도 포함돼 있었다** —
④문서가 처음에 근거를 잘못 적는 바람에 놓칠 뻔한 이 전략의 실질적 이점이다.

**재확인(2026-07-18).** ⑤ 브랜치 작업 중 같은 부하를 ④에 다시 인가해 검증했다. `cap=1 cont=200`
과 `cap=100 cont=120` 두 지점 모두 KO 0건이었고, InnoDB `lock_deadlocks` 카운터 증가분은
**0**이었다(앱 로그의 데드락·락 타임아웃도 0건). 결과는 그대로이고 근거만 바로잡은 것이다.

## 4. 검증 — 성능, 그리고 측정의 한계

### 4-1. 현재 정본 — 방법론 v2의 Phase 내부 비교

현재 표의 집계 단위는 **실행별 평균 응답의 중앙값 (min–max)** 이며 각 셀은 10회다.

| Phase | 경합 | ② 조건부 UPDATE | ④ 비관적 락 | Phase 내부 라운드별 관측 |
|---|---|---:|---:|---|
| A | 낮음 (`cap=100 cont=120`) | 125.5ms (119–146) | 152ms (139–160) | ② 9회 · ④ 1회 |
| A | 극단 (`cap=1 cont=200`) | 117ms (109–164) | 88.5ms (76–95) | ④ 10회 |
| B | 낮음 (`cap=100 cont=120`) | 126ms (119–142) | 140ms (134–166) | ② 9회 · ④ 1회 |
| B | 극단 (`cap=1 cont=200`) | 122.5ms (109–142) | 97.5ms (87–137) | ④ 9회 · ② 1회 |

라운드별 비교는 같은 캠페인·Phase·측정 라운드·경합 안에서만 연결했다. 그러나 ②와 ④는 같은
순간의 병렬 쌍이 아니라 Williams 순서의 **서로 다른 직렬 위치**에서 실행됐다. 위치와 실행 시점
차이가 남으므로 관측 차이를 오직 잠금 방식 때문이라고 돌리지 않는다. 낮은 경합과 극단 경합에서
방향이 반복해 달랐다는 이 측정은 “비관적 락은 언제나 느리다”는 일반화를 뒷받침하지 않는다.

| 낮은 경합<br>`cap=100 cont=120` | ④ 비관적 | 315, 386, 405, 197, 279, 237, 187 | **279** | 187–405 |
| | ② 조건부 | 175, 204, 178, 352, 172, 121, 180 | **178** | 121–352 |
| 극단 경합<br>`cap=1 cont=200` | ④ 비관적 | 308, 115, 127, 139, 80, 131, 74 | **127** | 74–308 |
| | ② 조건부 | 263, 119, 364, 205, 155, 101, 207 | **205** | 101–364 |

**읽는 법 — 과장하지 않는다.**

- **이 예비 측정의 낮은 경합에서는 ②가 일관되게 빨랐다.** 7쌍 중 6쌍에서 ②가 앞섰고 중앙값이 **178 vs 279ms**다.
  방향이 아래 4-3의 비용 구조와 일치한다 — 이 지점은 120건 중 100건이 실제로 INSERT까지 가는
  **성공 경로 우세** 구간이고, 성공 경로에서는 ④가 쿼리를 하나 더 쓴다(4 vs 3). 게다가 ④는 락을
  트랜잭션 시작부터 커밋까지 쥐고 있어 그 보유 시간이 그대로 대기열 길이가 된다.
- **극단 경합에서는 방향이 뒤집혔지만, 이 예비 측정으로는 확정할 수 없다**(중앙값 127 vs 205ms).
  두 범위가 74–308 / 101–364로 **완전히 겹치기** 때문이다 — 실행 간 편차가 전략 간 차이보다 크므로
  **여기서 어느 쪽이 빠르다고 단정하지 않는다.** 다만 뒤집힐 **이유는 실재한다**(4-3) — 이 지점은
  200건 중 199건이 거절되는 **거절 경로 우세** 구간이고, 거절 경로에서는 비용 구조가 반대다.
- **이 예비 측정의 한계를 명시한다.** Gatling·앱·MySQL이 한 노트북에 함께 돌고, 버스트 한 번
  (120~200건)의 평균이라 JIT 워밍업과 스케줄링 노이즈가 크게 섞인다. 이 표가 말할 수 있는 것은
  **당시 7쌍에서 ②가 저경합에서 일관되게 빨랐다**는 사실까지다. `methodology-v1-fixed-order`에서는
  재현되지 않았고 방법론 v2에서는 같은 방향이 다시 관측됐지만, 이 예비 숫자 자체를 현재 전략의
  성능 결론으로 승격하지 않는다.

### 4-3. 비용은 경로마다 방향이 다르다 (쿼리 수 실측)

"④가 왕복을 더 쓴다"는 서술은 **성공 경로에만 맞다.** MySQL general log 로 요청 1건이 실제로
발생시키는 쿼리를 세어 보면 거절 경로에서는 반대다.

| 경로 | ② 조건부 | ④ 비관적 |
|---|---|---|
| 성공(자리 있음) | **3** | 4 |
| 거절(만석) | 3 | **2** |

```
② 거절: applicant SELECT → UPDATE(0행) → select count(*)   ← existsById 추가 왕복
④ 거절: applicant SELECT → SELECT ... FOR UPDATE → throw
```

②는 UPDATE 가 0행일 때 **만석**인지 **없는 슬롯**인지 구분하려고 `existsById` 를 한 번 더 던진다.
④는 엔티티를 이미 손에 쥐고 있어 그 왕복이 없다. 게다가 MySQL 기본 격리 수준이 REPEATABLE READ 라
②의 UPDATE 가 잡은 행 락은 **커밋까지 유지**되므로, 그 추가 SELECT 는 락을 쥔 채로 나간다.

그래서 `capacity=1` 처럼 **거절이 지배적인** 부하에서는 추가 왕복을 치르는 쪽이 오히려 ②다. 위
극단 경합 수치가 뒤집힌 것은 노이즈일 수도, 이 구조 때문일 수도 있다 — **구분할 근거가 이 측정에
없을 뿐 메커니즘은 실재한다.** v2 반복 측정에서도 방향은 같았지만, `existsById`만 분리한 A/B가
아니므로 인과 확인은 여전히 후속 과제다.

**이 결과만으로 방어 메커니즘의 우열을 확정하지 않는다.** `existsById` 는 방어가 아니라 404와 409를
구분하려고 넣은 조회이고, 거절 경로에서 ②에만 한 번 더 붙는다. 이 구조는 v2의 극단 경합에서
관측한 ④의 더 작은 응답값과 방향이 맞지만, 조회만 분리한 A/B가 없고 Phase 내부 비교에도 직렬
위치·시점 차이가 남으므로 원인이나 제거 후 격차 소멸을 단정할 수 없다.
②는 이미 머지된 측정 기준이므로 여기서 손대지 않고 별도 후속 과제로 남긴다.

**현재 선택은 성능 순위가 아니라 문제 모양에 근거한다.** ②·④의 정합성과 가용성은 동률이고,
측정 성능은 ④가 같거나 빠른 구간도 있었다. 그 사실을 인정한 뒤에도 현재 불변식에는 보호할 별도
read→check→write 구간이 없고, 조건부 DML 한 문장이 곧 임계 구역이다. 그래서 기본 선택은 더 작은
②로 두되, 만석 거절 지연이 핵심 SLO이거나 불변식이 여러 문장으로 확장되면 ④를 다시 후보로 올린다.

## 5. 그래서 무엇이 남는가

이 브랜치의 산출물은 "비관적 락으로 오버부킹을 고쳤다"에서 끝나지 않는다. **현재의 한 행 산술
가드는 조건부 DML로 충분하고, 여러 문장을 함께 보호해야 할 때 비로소 명시적 락의 보장이 필요하다**는
경계를 코드와 측정으로 확인한 것이다.

- **락이 사는 것**: "읽은 것이 커밋까지 변하지 않는다"는 보장. read→check→write를 코드 모양 그대로
  두고 안전하게 만든다 — 한 문장으로 접을 수 **없는** 로직에 유일하게 쓸 수 있는 수단이다.
- **락이 치르는 것**: 대기열, **트랜잭션 길이만큼의 락 보유**, 트랜잭션 경계와의 결합, 다중 자원일
  때의 데드락 위험. (왕복 수 자체는 경로마다 방향이 달라 락의 고정 비용이 아니다 — 4-3 참고.)
- **이 도메인의 계산**: 현재는 접을 수 없는 로직이 없어 명시적 잠금 보장의 추가 가치가 없다. 다만
  극단 거절 경로의 지연처럼 실제 SLO에서 측정 이점이 있으면 그 이점과 구조적 비용을 다시 비교한다.

이 계산이 뒤집히는 지점은 [STEP2-CONDITIONAL-UPDATE.md](STEP2-CONDITIONAL-UPDATE.md) 6절 표의 첫
번째 행 — 불변식이 여러 행·여러 문장에 걸치는 순간이다. 예를 들어 "예약 확정 + 지원자별 전체 쿼터
차감 + 감사 로그"를 원자적으로 묶어야 한다면, 그 셋을 하나의 조건부 UPDATE로 접을 방법이 없으므로
그때는 `SELECT ... FOR UPDATE`가 정답이 된다. **이 프로젝트가 그 자리에 있지 않을 뿐이다.**
