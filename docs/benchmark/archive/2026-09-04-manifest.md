## 아카이브한 이유

당시 재현 명령은 기본 프로필의 `./gradlew bootRun`이었다. 따라서 HikariCP 풀 크기는
라이브러리 기본값에 맡겨졌고, Hibernate `show_sql`·SQL 포맷·SQL 주석과 바인드 TRACE 로그가
켜진 상태였다. 전략마다 SQL 횟수가 다른데 이 콘솔 I/O와 좁은 풀의 직렬화 비용이 함께 측정돼,
전략 자체의 비용만 비교했다고 볼 수 없다.

현재 정본은 `benchmark` 프로필로 풀을 100개까지 미리 준비하고 SQL 계측 로그를 끈 뒤 다시
측정한다. 이 파일들은 결론의 근거가 아니라, 왜 재측정했는지 추적하기 위한 역사 자료다.
