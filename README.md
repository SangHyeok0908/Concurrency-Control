# 선착순 면접 예약 시스템 — 동시성 제어 실험

## 프로젝트 목적

SSOC 프로젝트에서 선착순 면접 예약 기능을 구현하며 **설계 단계부터 비관적 락을 적용했습니다.** 당시 비관적 락·낙관적 락·분산 락의 이론적 장단점을 비교했고, 동시 요청을 직렬화해 정합성을 보장할 수 있다는 이유로 비관적 락을 선택했습니다.

하지만 비관적 락을 기다리는 요청도 대기하는 동안 DB 커넥션을 점유합니다. 같은 슬롯에 요청이 몰리면 커넥션 풀이 고갈되고, 해당 슬롯과 관계없는 요청까지 커넥션을 얻지 못해 서비스 전체가 느려질 수 있습니다. 여기서 **이 예약 기능에 비관적 락이 꼭 필요한가?**라는 의문이 생겼습니다.

이번 프로젝트는 락 없는 예약 로직의 동시성 문제를 직접 재현하고, SSOC에서 이론적으로 선택했던 비관적 락을 실제 동시 요청 환경에서 다시 검증하는 실험입니다. 여러 방어 전략을 같은 조건에서 비교해 각 방식이 적합한 상황과 치러야 하는 비용을 실험 결과로 정리했습니다.

## 다루는 문제

| 문제 | 방어 |
|---|---|
| 같은 지원자의 중복 요청 | `UNIQUE(applicant_id, slot_id)` |
| 서로 다른 지원자의 마지막 자리 경쟁 | 조건부 UPDATE 또는 락 |

두 문제는 별개입니다. 락만으로 중복 요청을 막을 수 없고, UNIQUE만으로 정원 경쟁을 막을 수 없습니다.

## 실험 결과

락 없는 baseline에서는 정원 100명에 서로 다른 지원자 500명이 동시에 요청한 한 실행에서 **예약 113건**이 확정됐습니다. 정원 초과뿐 아니라 잔여석 불일치(lost update)와 데드락도 관찰했습니다. [1단계 재현 기록](docs/STEP1-GATLING-LOADTEST.md)

이후 정원 경쟁을 5개 전략·두 경합 조건에서 총 200회 측정했습니다. 아래는 그중 **Phase B(낙관적 락 재시도 상한 20)**의 정원 방어 전략 비교입니다. 응답시간은 조건별 10회 실행에서 구한 **평균 응답시간의 중앙값**이며, 정수 ms로 반올림했습니다.

| 전략 | 100석 / 120명 | 1석 / 200명 | 관찰 |
|---|---:|---:|---|
| 조건부 UPDATE | 126ms | 123ms | 두 조건에서 정원을 채우고 오버부킹·요청 실패 없음 |
| 비관적 락 | 140ms | 98ms | 정합성은 동일하며, 1석 경쟁에서는 조건부 UPDATE보다 빠름 |
| 낙관적 락 | 483ms | 73ms | 1석 경쟁에서는 빠르지만, 여러 좌석을 채울 때 재시도 비용이 큼 |

방어 없는 경로와 UNIQUE만 적용한 경로는 정원 초과를 막지 못했습니다. 낙관적 락 상한 5를 측정한 Phase A에서는 100석을 채우는 동안 재시도 소진으로 요청이 실패했습니다. Phase A/B는 별도 앱 기동이므로 상한 변경만의 효과로 단정하지 않습니다.

동일 `(지원자, 슬롯)` 요청은 별도 25회 실험으로 검증했습니다. 전역 UNIQUE 덕분에 모든 경로가 예약 1건·좌석 소모 1개를 지켰지만, 중복 요청을 HTTP 409로 처리한 경로는 `/unique`뿐이고 나머지는 500을 반환했습니다.

전체 수치·편차·측정 조건·원시 데이터는 [방어 전략 벤치마크](docs/STEP2-DEFENSE-BENCHMARK.md)에 있습니다. 위 비교는 커넥션 풀 100개를 고정한 단일 슬롯 부하 실험이며, **풀 고갈이 무관한 요청에 미치는 영향까지 직접 측정한 결과는 아닙니다.**

## 트레이드오프와 최종 선택

**최종 선택은 `UNIQUE` + 조건부 UPDATE입니다.** 중복 요청은 DB 제약으로, 정원 경쟁은 `UPDATE ... WHERE remaining > 0`으로 방어합니다. 현재 불변식이 단일 슬롯 행의 정원 확인과 차감이므로, 이를 한 SQL로 표현할 수 있다는 점이 선택 이유입니다.

비관적 락이 항상 느린 것은 아닙니다. 측정에서도 1석 경쟁에서는 조건부 UPDATE보다 빨랐습니다. 두 경로의 SQL과 실행 시점도 달라 차이를 락 하나의 효과로 단정할 수 없습니다. 조건부 UPDATE 역시 InnoDB 행 잠금을 사용하므로 잠금 대기나 커넥션 점유 자체를 없애는 해법은 아닙니다.

다중 행·다단계 트랜잭션에서는 비관적 락을, 충돌이 드물고 재시도가 저렴한 경우에는 낙관적 락을 다시 검토할 수 있습니다. 현재는 자연 키와 단일 DB로 문제를 다룰 수 있어 [멱등성 키](docs/STEP2-3-BRANCH-STRATEGY.md#skip-idempotency-key)와 [분산 락](docs/STEP2-3-BRANCH-STRATEGY.md#skip-distributed-lock)은 도입하지 않았습니다.

후속 API 과제는 중복 재요청에 `200 + 기존 예약`을 반환하는 계약과, 조건부 UPDATE의 만석·없는 슬롯 구분 조회 비용을 별도 실험으로 확인하는 것입니다. 트래픽 증가 시에는 인기 슬롯과 DB 쓰기 한계를 먼저 측정하고, 필요하면 요청 유입 제한이나 대기열을 검토합니다.

## 구현과 실행

Java 21 · Spring Boot 3.5.16 · Spring Data JPA · MySQL 8.0 · Flyway · Gatling · Gradle wrapper를 사용합니다. Redis 7은 컨테이너만 기동합니다.

락 없는 baseline을 보존하고 `ReservationStrategy` 구현체로 방어 전략을 추가했습니다. `POST /api/reservations/{strategy}`의 `baseline`, `unique`, `conditional`, `pessimistic`, `optimistic` 경로를 같은 부하로 비교합니다. 스키마 변경 이력은 [ERD와 Flyway 단계별 변화](docs/ERD.md)에 있습니다.

JDK 21과 Docker가 필요합니다.

```bash
docker compose up -d
./gradlew build
./gradlew bootRun
```

앱은 `localhost:8080`에서 실행됩니다. DB·Redis 기본 설정은 [`application.yml`](src/main/resources/application.yml)에 있으며 Spring 표준 환경 변수로 덮어쓸 수 있습니다. HTTP 부하 테스트는 앱 실행 후 `./gradlew gatlingRun`으로 시작합니다. 통제 벤치마크의 재현 절차는 [벤치마크 문서](docs/STEP2-DEFENSE-BENCHMARK.md#9-재현)를 따릅니다.
